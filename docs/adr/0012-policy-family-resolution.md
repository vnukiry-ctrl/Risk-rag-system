# ADR-0012: Policy-family resolution for same policy number, multiple periods

**Status:** Accepted
**Date:** 2026-09-17

## Context
`documents_db` (`main.py`) was keyed by `meta.get("policy_number") or meta.get("source_file")` at `/extract` time. Two real files sharing a policy number — a policy and its own renewal, endorsement, or invoice — collided on that key, and whichever file's metadata loaded later in `os.listdir()` order silently won, discarding the other's metadata entirely. This was already a documented known gap (README.md Milestone 2 known gaps; `golden_set.py`'s ALCOA108 and B0621FMOUN000426 `known_limitation` cases) with two real, observed instances in the actual document set: ALCOA108 (the policy vs. its Year-1 adjustment endorsement) and the Contingent Protective policy B0621FMOUN000426 (a 3-year policy vs. its own Year-1 installment invoice), where the invoice's numbers silently won and the 3-year total/period were lost.

Beyond the key-collision bug itself, there was no logic at all for the underlying case the collision was masking: a policy legitimately has multiple versions over time (renewals, endorsements, extensions), and a question that names the policy number without a year is inherently ambiguous about which version the user means. `find_relevant_source_files` (ADR-0004) would, if the collision were merely fixed with no further change, have started scoping to *every* version at once — blending one year's premium/limit with another's in the same retrieval. That's a worse failure than today's single-document overwrite: it's silent and plausible-looking rather than an obviously-missing fact.

## Decision
Two changes, made together because fixing the storage bug alone would have immediately surfaced the second problem:

1. **`documents_db` keyed by `source_file`, not `policy_number`.** Every uploaded file gets its own entry; no two files can collide on this key. `policy_number`-based grouping across documents is done separately, as a query-time lookup over `documents_db`, not as the dict's primary key.
2. **Policy-family resolution in `find_relevant_source_files`.** When a matched policy number belongs to more than one `documents_db` entry, that's treated as one policy with multiple period/version records, not multiple unrelated matches to union together:
   - If the question names a year that matches exactly one family member's period (checked against both the parsed ISO date and a raw-string year extraction, since LLM-extracted dates aren't always parseable), retrieval scopes to that one document, silently — nothing to disclose, the question already disambiguated.
   - Otherwise, retrieval scopes to the most recent member by parsed `period_to`/`period_from` (falling back to `extracted_date`/upload time when no date parsed at all — never guessed from an unparseable string), and a disclosure note is generated in code and appended to the answer, naming the other periods on file and inviting the user to ask by year.
   - `insurance_loader.py` gained `parse_flexible_date()` (free-text policy dates → ISO, covering the formats observed in this document set, `None` rather than a guess when unparseable), producing `period_from_iso`/`period_to_iso`; and a `document_role` extraction field (`original`/`renewal`/`endorsement`/`extension`/`cancellation`, defaulting to `original`, only set otherwise when the document itself says so) for future use distinguishing a genuinely new period from a same-period amendment.

## Alternatives considered
- **Fix only the key-collision bug, leave family resolution for later** — rejected: as noted in Context, this would have made retrieval quality worse, not better, by silently blending multiple periods' facts into one answer instead of at least surfacing one complete (if wrong) document's data.
- **Always require the user to specify a year when a policy has multiple versions** — rejected as poor UX for the common case (most questions mean "the current policy"); latest-by-default-with-disclosure serves that case while still surfacing the ambiguity instead of hiding it.
- **A dedicated `policy_families` store, built and maintained at extraction time** — rejected as premature: grouping by `policy_number` at query time over the existing `documents_db` is O(number of documents) and cheap at this project's scale; a dedicated store would be justified once the document count made that scan matter.
- **Let the LLM decide and state which version is "latest" in its answer** — rejected on the same grounds as this project's existing grounding/verification pattern (`verify_grounded_fields`): a fact this checkable should be computed deterministically, not trusted to the model to get right and remember to mention every time.

## Consequences
- The two real, previously-silent collisions (ALCOA108, B0621FMOUN000426) are fixed at the code level: both files now keep their own metadata in `documents_db`, and an unscoped question about either policy resolves to the most recent period with the other disclosed, rather than one file's data vanishing. **B0621FMOUN000426 re-verified 2026-09-21** against a live `/extract` + `/query` run on the real documents: both files kept separate metadata, and an unscoped question about the policy correctly resolved to the real 3-year policy (CAD 12,987) with a disclosure note naming the Year-1-invoice version, not the invoice's $4,329 — `golden_set.py`'s case for this was promoted from `known_limitation` to a scored `structured_fact`. **ALCOA108 not yet re-verified**: its adjustment-endorsement file (`25-26 Automobile 21B Adjustment ALCOA108.pdf`) hit Groq's per-minute token rate limit during the same verification run and has no prior successful extraction to fall back on, so it's currently an error record in `documents_db.json` rather than live-tested data; that case's note in `golden_set.py` still says "not yet re-verified."
- **A second real gap found and fixed during that same verification pass**: `parse_flexible_date()` didn't handle ordinal day suffixes ("28th July 2026", "1st July 2029") — the actual format the real 3-year policy's dates use. Silently returning `None` for these sent `_sort_key` to its `extracted_date` fallback tier, which ranked the (correctly-parsed, but shorter) Year-1 invoice period above the (unparsed, but genuinely later) 3-year policy — exactly the wrong-document failure mode this ADR exists to prevent, caused by the date parser rather than the resolution logic itself. Fixed by allowing an optional `(?:st|nd|rd|th)?` after the day number in both ordinal-date regexes.
- `document_role` is extracted but not yet consumed by any scoping logic. An endorsement that doesn't change `period_to` at all (a real possibility) would only be picked as "latest" if it happens to sort that way by date, not because its role was recognized. Preferring the most recent endorsement/extension over a same-dated original by consuming `document_role` is a natural follow-up, not built here.
- `parse_flexible_date`'s month-first-unless-impossible default is tuned to this project's observed document formats (`07/01/2026` meaning July 1). Documents from a day-first-convention market would need that default flipped — the same kind of domain-specific tuning already flagged elsewhere in this codebase (e.g. `insurance_loader.py`'s declarations-keyword list).
- Generalizes the same way ADR-0004 did: any RAG system where records can legitimately supersede each other over time (contract renewals, amended filings, policy versions) needs this same "resolve to one version, disclose the rest" pattern rather than either blending versions together or picking one silently.
