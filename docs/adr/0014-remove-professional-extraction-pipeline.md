# ADR-0014: Remove the professional (classify-then-target) extraction pipeline

**Status:** Accepted
**Date:** 2026-09-28

## Context
The original (and, after this ADR, only) metadata-extraction pipeline (`insurance_loader.py`'s `head_truncate` strategy) sends the LLM a blind `text[:8000]` sample of each document. That's a real, previously-documented gap: `tests/golden_set.py`'s Excess Side A D&O `known_limitation` case is a document whose actual declarations page sits on page 17 of 44, behind ~16 pages of insurer privacy-policy boilerplate, so every structured field comes back null for it -- the first 8000 characters never reach real content.

To address that, a second pipeline was added: `classify_then_target`, built around `select_declarations_window()`. Instead of taking the first 8000 characters, it split each document into overlapping 2000-character windows, scored each by declarations-vocabulary density (multi-word structural labels like "named insured:", "policy period:" immediately followed by a colon and a value, plus `$`/date density as secondary signal), and stitched together the highest-scoring windows -- restored to original document order -- up to the same 8000-character budget. The intent was to reach the real declarations page wherever it actually sits, not just at the front of the file.

It was exposed as a fully parallel pipeline rather than a replacement: `POST /extract/professional` + `GET /documents/professional`, a separate `documents_db_professional` in-memory dict, a `store="professional"` row family in Postgres (`documents`/`policy_data`/`field_verifications`, alongside `store="default"`), and a second "Professional Way" tab in the Streamlit frontend -- run side by side against the same 16 real documents (Mount Royal University's actual insurance program) so the two strategies' output could be compared directly instead of one overwriting the other. Based on the earliest `extracted_date` values observed in the professional store, it was first used locally (as `documents_db_professional.json`, before the 2026-09-24 Postgres migration committed the feature to git) starting around 2026-09-14.

## Decision
Remove the professional pipeline entirely: the `/extract/professional` and `/documents/professional` endpoints, the `documents_db_professional` in-memory store, its `store="professional"` rows in Postgres, the frontend's second tab, and the window-scoring code it depended on (`select_declarations_window`, `_score_window`, `_LABEL_RE`, `_DECLARATIONS_KEYWORDS`, `_DATE_PATTERN`). `/extract` / `/documents` (`head_truncate`) is the only extraction path going forward.

This is based on a direct comparison against the real 16-document set and the hand-verified facts in `tests/golden_set.py` (each fact checked directly against the source PDF's declarations page, not against either pipeline's own output):

- **Self-grounding rate** (does the LLM's claimed source quote actually appear in the text it was given), across every scored field on all 16 documents: general 95.8% (138/144) vs. professional 90.5% (105/116, excluding 2 documents professional produced no row for at all that run).
- **Golden-set correctness**, first comparison run: general 11/13 (85%) vs. professional 8/13 (62%).
- **A confirmed factual error, not just a gap**: professional extracted a $10,000,000 limit of liability for the Excess Liability cover note (policy SPRGL2602187). The document's declarations page states `LIMIT OF LIABILITY: CAD 40,000,000 Each Occurrence` (re-extracted directly from the PDF to confirm) -- professional's window-selection had picked up one of several `Limit of Liability: CAD 10,000,000` lines from the underlying-insurers schedule elsewhere in the document instead. General correctly extracted $40,000,000 for the same document.
- **A reliability regression on re-run**: after an unrelated bug fix (main.py reloading `documents_db` from Postgres before merging, instead of accumulating stale in-memory state), professional was re-run and dropped further, to 6/13 (46%). Three documents that had previously extracted correctly or partially (User Group AVP406486, the Factory Mutual property policy, and a second attempt at the Excess Liability policy above) failed outright with either `429` (Groq's 8000-tokens-per-minute limit) or truncated/malformed JSON responses. Both failure modes trace to professional's stitched-window input being larger and denser than `head_truncate`'s, combined with `insurance_loader.py` having no retry/backoff on a transient rate-limit error.
- **One genuine, undisputed win**: professional did reach further into the one document `head_truncate` structurally cannot reach at all -- the Excess Side A D&O policy (declarations on page 17 of 44). It recovered a real `policy_number` and `insured_name`/`insured_address` for that document that general (correctly, given its design) returns entirely null for. It still did not recover that document's limit, premium, or dates.

## Alternatives considered
- **Fix the reliability issues (retry/backoff on 429, raise `max_tokens`, throttle between documents) and keep both pipelines side by side** -- rejected for now. Not because it's unfixable, but because even setting reliability aside, professional made one confirmed factual extraction error ($10M vs. the real $40M) that general's simpler design never made on this document set, while adding a second scored, stored, and UI-exposed pipeline to maintain. Worth revisiting if a future document set has more than the one case where `head_truncate`'s blind-truncation gap actually bites.
- **Keep professional as the primary pipeline and retire `head_truncate` instead** -- rejected: professional currently scores worse on the hand-verified golden set by a wide margin (46-62% vs. general's steady 85%), which would be a regression in answer correctness, not an improvement, despite the more sophisticated design intent.
- **Stop calling `/extract/professional` but leave the code and endpoints in place** -- rejected. An endpoint nobody's supposed to call, that still fires real LLM requests and writes to Postgres if anyone (or anything) hits it, is a silent surface this project has repeatedly flagged as a real risk elsewhere (`docs/learning-guide.md` 5.6, "fail loudly, not silently"). Dead-but-reachable code is worse than removed code.

## Consequences
- `/extract/professional` and `/documents/professional` no longer exist; any caller relying on them gets a 404. The Streamlit frontend's Documents page is back to a single view instead of two tabs.
- `documents.store` (and `policy_data`/`field_verifications`, keyed off it) keeps its generic `store` column rather than being collapsed to a single-store schema -- removing it would need an Alembic migration touching already-populated production data for a column that's harmless to leave as-is, always `"default"` going forward.
- The one real gap professional partially addressed -- `head_truncate` structurally cannot reach a declarations page sitting past the first 8000 characters -- is fully unaddressed again. The Excess Side A D&O policy's structured metadata (`policy_number`, `insured_name`/`insured_address` included) is null again in the only remaining pipeline. This is the same `known_limitation` already documented in `golden_set.py` and README's Milestone 2 known gaps; nothing about that specific document got worse, it simply stops being partially better.
- If this gap needs solving again, `select_declarations_window`'s window-scoring approach is preserved here and in git history (commit `71d62ec`), not lost. A future attempt should fix the two concrete failure modes found in this comparison -- add retry/backoff on Groq `429`, and either raise `max_tokens` or otherwise avoid truncated JSON on its denser input -- and re-verify against the golden set before shipping it as a parallel production pipeline again, rather than repeating the sequence this ADR documents.
